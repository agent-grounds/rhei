# Rhei PM Review - 2026-04-22

This file is an archived hands-on review of the `rhei` CLI as it existed on
April 22, 2026. It exercised the main user-visible workflows:
`templates`/`instantiate`, `validate`, `render`, `next`, `transition`,
`complete`, `reset`, `run --dry-run`, and `install-skills`.

As of May 20, 2026, the old issue list has been reconciled. Current planned
work lives in the roadmap. [§RM-rhei-roadmap](../roadmap.md#rm-rhei-roadmap-roadmap)

## Moved to Roadmap

These review findings remain meaningful follow-up work and are now tracked in
the roadmap:

- Parser diagnostics should accumulate multiple markdown parse errors in one
  run. [§FS-rhei-plan-language](rhei-plan-language.spec.md#fs-rhei-plan-language-rhei-plan-language-specification) [§FS-rhei-validate](rhei-validate.spec.md#fs-rhei-validate-rhei-validate)
- `rhei complete` should explain loop-condition failures with concrete
  condition values and available next transitions. [§FS-rhei-complete](rhei-complete.spec.md#fs-rhei-complete-rhei-complete) [§FS-rhei-transitions](rhei-transitions.spec.md#fs-rhei-transitions-rhei-transitions-specification)
- `rhei transition` result-file behavior needs one consistent product choice:
  no result file for bare transitions, or linked/audited result files matching
  `rhei complete`. [§FS-rhei-transition-cmd](rhei-transition-cmd.spec.md#fs-rhei-transition-cmd-rhei-transition) [§FS-rhei-complete](rhei-complete.spec.md#fs-rhei-complete-rhei-complete)
- Template UX still has planned polish: empty template search output should
  list searched paths, nested `--list-inputs` defaults should be copyable, and
  reusable values-file scaffolds should be easier to discover. [§FS-rhei-templates](rhei-templates.spec.md#fs-rhei-templates-rhei-templates-specification)
- `type: path` semantics need a final product decision around default values,
  relative/absolute rendering, and whether `--allow-missing-paths` should exist. [§FS-rhei-templates](rhei-templates.spec.md#fs-rhei-templates-rhei-templates-specification)
- JSON errors now have a JSON envelope, but a stable `kind` and optional `path`
  taxonomy still need design before integrations depend on them. [§FS-rhei-render](rhei-render.spec.md#fs-rhei-render-rhei-render)
- Small output cleanups remain useful: separate agent/model display, validation
  source wording, state-instruction variable conventions, and the rendered JSON
  `metadata.metadata` shape. [§FS-rhei-next](rhei-next.spec.md#fs-rhei-next-rhei-next) [§FS-rhei-validate](rhei-validate.spec.md#fs-rhei-validate-rhei-validate) [§FS-rhei-states](rhei-states.spec.md#fs-rhei-states-rhei-states-specification) [§FS-rhei-render](rhei-render.spec.md#fs-rhei-render-rhei-render)

## Resolved or Stale

These April findings are no longer tracked as open roadmap work:

- Plain-file `rhei reset` cleanup parity is implemented and specified:
  reset removes runtime-owned result links, assignees, and the adjacent
  `runtime/` directory for both single-file plans and directory workspaces. [§FS-rhei-reset](rhei-reset.spec.md#fs-rhei-reset-rhei-reset)
- `rhei transition` checks the task's current state against `--from` before
  reporting transition-legality errors, so stale `--from` values produce an
  actionable conflict. [§FS-rhei-transition-cmd](rhei-transition-cmd.spec.md#fs-rhei-transition-cmd-rhei-transition)
- Progress rendering honors terminal detection, `NO_COLOR`, and `--no-color`. [§FS-rhei-render](rhei-render.spec.md#fs-rhei-render-rhei-render)
- `rhei next --peek` exists and is documented as a read-only inspection mode. [§FS-rhei-next](rhei-next.spec.md#fs-rhei-next-rhei-next)
- `rhei next` writes `**Assignee:**` on claim, refuses already assigned tasks,
  and `rhei complete` / `rhei reset` remove runtime-owned assignee lines. [§FS-rhei-next](rhei-next.spec.md#fs-rhei-next-rhei-next) [§FS-rhei-complete](rhei-complete.spec.md#fs-rhei-complete-rhei-complete) [§FS-rhei-reset](rhei-reset.spec.md#fs-rhei-reset-rhei-reset)
- `rhei next` no-claim diagnostics distinguish terminal, gated, in-flight,
  mid-workflow, and prerequisite-blocked states; mid-workflow diagnostics list
  concrete transition commands. [§FS-rhei-next](rhei-next.spec.md#fs-rhei-next-rhei-next) [§FS-rhei-transition-cmd](rhei-transition-cmd.spec.md#fs-rhei-transition-cmd-rhei-transition)

## Review Value

The review remains useful as historical evidence for why the roadmap emphasizes
predictable execution, repeatable template UX, and monitoring clarity. New
planning should start from `docs/roadmap.md`, not from the
original unchecked issue order in this archived review. [§GOAL-rhei-outcomes](../goals.md#goal-rhei-outcomes-goals)
